Missing:
- На статическом сайте нужны отдельные документы/акцепты: политика обработки персональных данных, purpose-specific согласие на VK-привязку/friend graph и пользовательское соглашение; email-рекомендации требуют ещё одного независимого opt-in. — Статус: `Не выполнено`

Допустимая целевая формулировка — минимальное хранение: без message body, без полного friend list, с encrypted VK ID/dedicated HMAC lookup, TTL и удалением/отзывом. — Статус: `Требует юридического согласования`
- Нужен server-side challenge/receiver flow: создание challenge по авторизованному site subject из YDB personal-data contour, приём только новых входящих сообщений строгого формата, atomic consume, one-to-one VK↔site-account conflict/recovery semantics, dedupe и abuse protection. Возможный Supabase JWT считается только transitional auth assertion до отдельного localization-аудита и не является хранилищем VK-ПДн. Статический Astro frontend сам по себе этот flow выполнить не может. — Статус: `Не выполнено`

Supabase, core Fly SQLite, YDB analytics и статические артефакты не должны хранить или зеркалировать raw VK ID, message body, полный friend list либо identity graph. — Статус: `Направление подтверждено пользователем 2026-07-13, схема не реализована`

Needs clarification:
- Production-инцидент от `2026-06-15`: ручная сверка показала, что неверное определение количества штампов является массовым явлением, а не единичной ошибкой отдельной заявки. OCR/LLM-подсчёт нельзя считать достаточным источником истины без операторской проверки спорных случаев. — Статус: `Не выполнено`
- Уточнение production-инцидента от `2026-06-20`: пользователи массово жалуются именно на занижение количества штампов. Косвенное подтверждение из production-backup diff: среди найденных ручных исправлений `11` из `12` заявок были увеличением количества штампов, суммарная дельта `+35`; OCR/LLM-значение нужно считать предварительным нижним/ошибочным значением до операторской сверки. — Статус: `Не выполнено`
- Для заявок на розыгрыш нужен явный операторский сценарий ручной корректировки количества штампов с пересчётом баллов, неявок и веса в розыгрыше до публикации результатов. — Статус: `Не выполнено`

Missing:

- Нужен отдельный статус `needs_manual_review`/эквивалент для OCR-результатов по штампам: пользовательский и операторский интерфейсы должны явно отличать предварительное машинное распознавание от подтверждённого оператором количества. — Статус: `Не выполнено`
- Нужна защита от недосчёта штампов: сохранять достаточно детальные исходные изображения для операторской проверки, не ухудшать мелкие/бледные штампы чрезмерным клиентским сжатием и не использовать OCR/LLM как финальный источник при бледных, перекрывающихся, частично обрезанных или перспективно искажённых штампах. — Статус: `Не выполнено`
- Нужен технический журнал ручных корректировок штампов, чтобы production-правки не оставались только прямым изменением SQLite-строк. — Статус: `Не выполнено`

- Все VK API вызовы должны идти через локальный rate-limit wrapper с паузой около `1100ms` и retry/backoff на VK `error_code=6`. — Статус: `Реализовано в коде, не подтверждено пользователем`

- Детерминистический матчинг ФИО может использовать только явные безопасные алиасы имени в позиции имени (`Анна` ↔ `Аня`/`Анюта`, `Татьяна` ↔ `Таня`) и узкую односимвольную опечатку/усечение фамилии при точном/алиасном совпадении имени. Широкие prefix/fuzzy совпадения фамилии не должны автоматически становиться `matched`; они остаются `weak`/`ambiguous` для LLM или ручной проверки. — Статус: `Реализовано в коде, не подтверждено пользователем`

- Результаты LLM/детерминистики должны кэшироваться по `vk_user_id` и snapshot display-name, чтобы не сверять одного VK-пользователя повторно без изменения имени. При этом runtime должен использовать из cache только уверенные `matched`: старые `weak`/`ambiguous`/`unmatched` не должны блокировать более точные правила матчинга или появившиеся позже спецзаявки. — Статус: `Реализовано в коде, не подтверждено пользователем`
- По итогам каждого scheduled/manual production run должен формироваться Telegram-отчёт для superadmin за последние `24` часа: статистика, список сопоставленных ФИО спецзаявок и какие активности сделал каждый человек. Уточнение после production-дефекта от `2026-06-16`: отчёт не должен выглядеть пустым/ошибочным, если точных timed-активностей мало, но скан впервые нашёл лайки/копии; такие активности нужно показывать отдельным блоком. - Production-дефект от `2026-06-27`: отчёт соцактивности не должен сводить найденного VK-актора только к первой исторической спецзаявке `Этюды той весны`, если этот же человек подал заявки на другие спецмероприятия. Старый `unmatched`/`ambiguous` cache не должен блокировать появившиеся позже спецзаявки. — Статус: `Реализовано и задеплоено на production, не подтверждено пользователем`
