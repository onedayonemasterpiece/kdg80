## Терминология

- Пользовательская формулировка: `Заявка на розыгрыш`, не `регистрация на событие`. — Статус: `Зафиксировано`
- Заявка не является билетом и не гарантирует проход на спецмероприятие. — Статус: `Зафиксировано`
- После успешной заявки пользователь участвует в розыгрыше выбранных дат, а победители получают место на конкретный показ. — Статус: `Зафиксировано`
- Количество мест показа и количество мест в розыгрыше не является лимитом принимаемых заявок: если доступность заявки не закрыта отдельным состоянием, прошедшей датой или опубликованным розыгрышем, система продолжает принимать заявки от всех участников, выполнивших условия; победителей выбирает розыгрыш из всего допущенного пула. — Статус: `Зафиксировано`
- Текст успешного экрана должен прямо объяснять, что это ожидание розыгрыша, а не билет; пользователь может сделать скриншот подтверждения. — Статус: `Зафиксировано`

## Спецмероприятие `Этюды той весны`

- Каноническое название: `Этюды той весны`. — Статус: `Зафиксировано`
- Формат: иммерсивный спектакль. — Статус: `Зафиксировано`
- Площадка: `Южный Вокзал`. — Статус: `Зафиксировано`
- Публичная локация спектакля не должна скрываться как `Секретная локация`: в карточке и на странице события нужно показывать `Южный вокзал`, `ул. Железнодорожная, 13/23`. — Статус: `Не подтверждено пользователем`
- Первая дата показа: `11 июня 2026, 18:00`. — Статус: `Зафиксировано`
- Второй показ: `23 июня 2026, 18:30`. — Статус: `Зафиксировано`
- Третий показ: `25 июня 2026, 18:30`. — Статус: `Зафиксировано`
- Для каждого показа нужна отдельная карточка даты внутри спецмероприятия. — Статус: `Не подтверждено пользователем`
- До завершения отладки форма подачи заявки не должна быть видима в основной production-навигации; доступ к подаче заявки идет по управляемой секретной ссылке и текущему состоянию доступности. — Статус: `Зафиксировано`
- На этапе секретной отладки страница заявки должна иметь `noindex, nofollow, noarchive` и не должна попадать в `sitemap.xml`, `llms.txt` или `llms-full.txt`. — Статус: `Не подтверждено пользователем`
- Секретный preview-деплой должен всегда проходить через preview URL rewrite: HTML/CSS/JS asset references, canonical и OG URL должны указывать на текущий preview prefix, а не на root; простая загрузка сырого `site/dist` в prefix запрещена, потому что ломает визуал и делает E2E по файлам недостоверным. — Статус: `Не подтверждено пользователем`
- После подтверждения готовности и переноса функционала с секретной страницы на публичный доменный URL страница спецмероприятия должна индексироваться как остальные страницы сайта: человекочитаемый канонический URL, SSR-контент о событии, meta description, Open Graph/Twitter, canonical и структурированные данные Schema.org. — Статус: `В доработке`
- Публичная страница события `Этюды той весны` должна отвечать SEO/GEO-требованиям: иметь вовлекающий SSR-текст, конкретные даты/место, OG-изображение той же айдентики, canonical и Schema.org-структуру с серией показов, чтобы событие было понятно поисковикам и AI-поиску как отдельная сущность фестиваля. — Статус: `Не подтверждено пользователем`
- После публичного открытия спецмероприятие должно быть учтено в SEO/GEO-артефактах сайта: sitemap, `llms.txt` и `llms-full.txt`, чтобы AI-поиск видел событие как отдельную сущность фестиваля. — Статус: `В доработке`
- Технические ticket-страницы, private storage, фото паспортов участника фестиваля и админские ссылки не должны попадать в индекс, sitemap или AI-ready списки. — Статус: `Зафиксировано`

## Квоты и брони

- На каждый показ разыгрывается до `30` мест, если для конкретной даты не задана отдельная бронь или квота. — Статус: `Зафиксировано`
- На показ `11 июня 2026, 18:00` разыгрывается `27` мест, потому что `3` места уже забронированы. — Статус: `Зафиксировано`
- Бронь должна храниться отдельно от количества разыгрываемых мест, чтобы отчеты показывали и физическую квоту, и число доступных мест розыгрыша. — Статус: `Не подтверждено пользователем`
- В пользовательской форме у каждой даты должно быть понятно, сколько всего мест физически, сколько мест в розыгрыше и сколько мест в брони, если бронь не равна 0. — Статус: `Не подтверждено пользователем`

- При добавлении точного дубля фото UI должен явно показать, что файл уже добавлен и не будет засчитан повторно. — Статус: `Не подтверждено пользователем`
- На мобильных браузерах чтение фото должно быть устойчивым: если `FileReader.readAsDataURL` не сработал, нужно использовать запасной способ чтения через `arrayBuffer` и показывать понятную ошибку только после обеих неудач. — Статус: `Не подтверждено пользователем`
- UI загрузки фото должен быть совместим с Android Chrome/WebView без зависимости от новых синтаксических возможностей JavaScript вроде optional chaining, и должен принимать фотографии из системного пикера/камеры даже если Android вернул пустой MIME type или `application/octet-stream`; точный формат JPG/PNG/WebP должен финально проверяться backend по заявленному типу, имени файла и сигнатуре байтов. — Статус: `Не подтверждено пользователем`
- UI загрузки не должен сбрасывать значение `input[type=file]` до завершения чтения выбранных файлов на Android Chrome/WebView; после успешного чтения base64 должен храниться в состоянии выбранного фото и переиспользоваться для preview, предварительной проверки и финальной отправки без повторного чтения локального file handle. — Статус: `Не подтверждено пользователем`
- Если Android Chrome/WebView не дает странице прочитать один или несколько выбранных файлов через `FileReader` и `arrayBuffer`, UI не должен оставаться в состоянии `Не удалось проверить`: форма должна отправить новые исходные `File` напрямую на backend через multipart endpoint для предварительной проверки, а backend должен вернуть `dataBase64`, чтобы UI заменил битый локальный preview на стабильный `data:` preview и мог дальше отправлять фото без повторного чтения локального file handle. — Статус: `Не подтверждено пользователем`
- Для последовательного добавления нескольких фото на Android Chrome/WebView нельзя полагаться на `Blob`/`slice`-кэш браузера: уже проверенные фото должны переотправляться как текстовое multipart-поле `photoData` с base64, новые фото — как реальные `File` текущего выбора, backend должен сохранять порядок этих частей; сценарии `1 фото -> добавить ещё`, `1 -> 2 -> 3+` и выбор нескольких фото сразу должны работать без `Failed to fetch`. — Статус: `Не подтверждено пользователем`
- Пока фотографии читаются, отправляются на backend или распознаются OCR/LLM, UI должен показывать отдельное состояние ожидания с динамическим индикатором и понятным текстом `идет проверка, подождите`; в этом состоянии не должны появляться красные ошибки, если идет штатный fallback или повторная проверка. — Статус: `Не подтверждено пользователем`
- Пользователь не должен видеть технические тексты исключений JavaScript, HTTP/fetch или невалидного JSON, включая `Failed to fetch`, `Cannot read properties...`, `null`, `undefined`; такие ошибки должны логироваться/обрабатываться как технические и заменяться человекочитаемым сообщением после исчерпания fallback-механики. — Статус: `Не подтверждено пользователем`
- Кнопка отправки заявки должна быть недоступна, пока идет предварительная проверка загруженных фото или пока нет ни одного фото с завершенной проверкой. — Статус: `Не подтверждено пользователем`
- Поясняющий текст загрузки:

```text
Приложите фотографию паспорта участника фестиваля с заполненным полем ФИО. Если у вас несколько экземпляров, пожалуйста, приложите несколько фотографий; ФИО должно быть заполнено и видно на каждой фотографии, чтобы нельзя было приложить чужой паспорт. Фотографии принимаются только с лицевой стороны.

У вас должно быть не менее 5 штампов о посещении событий фестиваля.
```

— Статус: `Зафиксировано`

## OCR и проверка паспорта участника

- После загрузки фото сразу запускается автоматическая проверка OCR/LLM через очередь без конкуренции за модельные и сетевые лимиты. — Статус: `Зафиксировано`
- До отправки заявки пользователь должен видеть предварительный результат OCR/LLM по загруженным фото: сколько фото загружено, сколько уникальных, сколько зачтено, сколько штампов распознано и сколько баллов предварительно будет начислено. — Статус: `Не подтверждено пользователем`
- Предварительный расчет должен быть отделен по формулировке от финального результата после нажатия `Отправить заявку`: до отправки это `предварительный расчет по фото`, после отправки это `итог заявки`. — Статус: `Не подтверждено пользователем`
- Предварительный расчет баллов должен пересчитываться после каждого добавления или удаления фото и показывать подсказку `Добавьте ещё фото, если у вас несколько экземпляров паспорта участника фестиваля`. — Статус: `Не подтверждено пользователем`
- Серверный endpoint предварительной проверки фото должен использовать ту же OCR/LLM-логику, дедупликацию и scoring-механику, что и финальная подача заявки, но не создавать заявку, не сохранять фото в private storage и не отправлять Telegram-уведомления. — Статус: `Не подтверждено пользователем`
- В registration-сервисе OCR/LLM-вызовы должны проходить через лимитер: последовательная очередь, настраиваемая пауза между запросами, retry/backoff на `429` и временные ошибки провайдера, без параллельной атаки на модель. — Статус: `Не подтверждено пользователем`
- В техническом результате OCR должен сохраняться след лимитера: provider/model, количество попыток, время ожидания в очереди и факт лимитированного запуска, чтобы можно было проверить, что вызов не ушел напрямую мимо контроля лимитов. — Статус: `Не подтверждено пользователем`
- Для отладки нужно поочередно проверить OCR через `gpt-4o-mini` и через доступную Gemma-модель на приложенных тестовых файлах. — Статус: `Зафиксировано`
- Тестовые файлы:
  - `/home/dev/projects/kdg80/Исходные данные/Спецмероприятия/IMG_20260606_090446.webp`
  - `/home/dev/projects/kdg80/Исходные данные/Спецмероприятия/IMG_20260606_090451.webp`
  - `/home/dev/projects/kdg80/Исходные данные/Спецмероприятия/IMG_20260606_090453.webp`
  — Статус: `Зафиксировано`
- Проверка должна определить, есть ли на фото заполненное поле ФИО. — Статус: `Зафиксировано`
- Проверка должна посчитать количество зачтенных штампов посещений. — Статус: `Зафиксировано`
- Минимум для допуска к розыгрышу: `5` зачтенных штампов. — Статус: `Зафиксировано`
- Минимум `5` штампов можно набрать любым способом по сумме всех зачтенных фотографий заявки; требование применяется не к каждой фотографии отдельно. — Статус: `Зафиксировано`
- Если на отдельной фотографии распознано заполненное ФИО, с этой фотографии засчитывается любое найденное количество штампов, включая `1-4`; если общая сумма по подписанным фотографиям меньше 5, фото считается зачтенным, но отправка заявки недоступна до добавления достаточного количества штампов. — Статус: `Зафиксировано`
- Если ФИО на отдельной фотографии не распознано, штампы с этой фотографии не засчитываются, даже если они видны; пользователь должен получить понятную подсказку: вписать ФИО в этот паспорт участника фестиваля и загрузить фото заново. Это защищает розыгрыш от прикладывания чужих паспортов. — Статус: `Зафиксировано`
- Если фото не подходит или общая сумма зачтенных штампов меньше 5, пользователь получает понятное сообщение вместо допуска к розыгрышу. — Статус: `Зафиксировано`
- Ручной проверки заявок в пользовательском потоке не предусматривается; спорные или неуверенно распознанные фото должны приводить к понятной автоматической ошибке и предложению загрузить более качественное фото. — Статус: `Зафиксировано`
- Точные confidence thresholds для автоматического принятия или отклонения фиксируются после OCR-отладки на тестовых файлах и реальных примерах. — Статус: `В доработке`
- Отдельные физически видимые штампы на одной странице считаются отдельными посещениями, даже если дизайн штампов одинаковый; уникальность дизайна штампа не является требованием. — Статус: `Не подтверждено пользователем`

## Дедупликация фото и штампов

- Пользователь может приложить одно и то же фото дважды; такие дубли нельзя засчитывать повторно. — Статус: `Зафиксировано`
- Пользователь может приложить разные фотографии одной и той же страницы паспорта; такие дубли нельзя засчитывать повторно. — Статус: `Зафиксировано`
- Дедупликация должна учитывать не только hash файла, но и содержимое изображения через LLM/OCR: совпадение страницы, расположение штампов, ФИО и визуальные признаки. — Статус: `Зафиксировано`
- В итоговом расчете хранится количество загруженных фото, количество уникальных зачтенных фото/страниц и количество зачтенных штампов. — Статус: `Не подтверждено пользователем`

## Баллы

- За первые `5` зачтенных посещений участник получает `10` баллов. — Статус: `Зафиксировано`
- За каждое зачтенное посещение сверх 5 участник получает еще `2` балла. — Статус: `Зафиксировано`
- Баллы участника являются общим весом в розыгрыше всей серии показов спецмероприятия, а не умножаются на каждую выбранную дату. — Статус: `Зафиксировано`
- Вес участника на конкретный показ считается как `баллы / количество выбранных дат`; если выбрана одна дата, весь вес работает на нее, если выбрано несколько дат, вес равномерно распределяется между ними. — Статус: `Зафиксировано`
- Для технического розыгрыша дробный вес масштабируется до целых технических билетиков без изменения пропорций; аудит должен показывать исходные баллы, количество выбранных дат, вес на показ, технический масштаб, диапазон билетиков и выпавший номер. — Статус: `Зафиксировано`
- Требование про пользовательскую галочку `я был волонтером фестиваля` отменено. — Статус: `Зафиксировано`
- Волонтерский бонус вводится после подключения списка волонтеров в системе. — Статус: `Не подтверждено пользователем`
- Сверка со списком волонтеров должна идти по ФИО с учетом возможных незначительных опечаток. — Статус: `Не подтверждено пользователем`
- Если участник совпал со списком волонтеров, бонус составляет `10` баллов. — Статус: `Не подтверждено пользователем`
- После успешной заявки участник должен видеть отдельную доброжелательную строку о том, что ему начислены `10` баллов за волонтерство. — Статус: `Не подтверждено пользователем`

## Штраф за неявки

- Количество регистраций участника на обычные события определяется по базе регистраций фестиваля через поиск по ФИО. — Статус: `Зафиксировано`
- Количество посещений участника определяется количеством зачтенных уникальных штампов на загруженных фото. — Статус: `Зафиксировано`
- Количество неявок считается как `количество найденных регистраций на события - количество зачтенных штампов`. — Статус: `Зафиксировано`
- В штрафе за неявки учитываются только обычные события, прошедшие до начала текущего календарного дня в часовом поясе фестиваля; будущие события и события сегодняшнего дня в штраф не включаются. — Статус: `Не подтверждено пользователем`
- Если полученное количество неявок меньше 0, для расчета штрафа используется 0. — Статус: `Зафиксировано`
- За неявки свыше `3` вычитается `3` балла за каждую такую неявку. — Статус: `Зафиксировано`
- Волонтерский бонус не участвует в штрафах за неявки: сначала рассчитываются баллы за штампы с учетом штрафа, затем прибавляется гарантированный волонтерский бонус. — Статус: `Не подтверждено пользователем`
- Для заявки, набравшей минимум штампов для допуска, баллы за штампы после штрафов не должны быть ниже `3`; волонтерский бонус прибавляется сверх этого минимума. Если минимум штампов не набран, заявка не допускается к розыгрышу независимо от положительного бонуса. — Статус: `Не подтверждено пользователем`
- Итоговые баллы не должны уходить ниже 0; заявка с 0 баллов не участвует в розыгрыше. — Статус: `Зафиксировано`
- Сверка ФИО с обычными регистрациями должна учитывать перестановку имени/фамилии и безопасные префиксные сокращения вроде `Лариса Че` -> `Четверикова Лариса`; такие совпадения должны считаться для штрафа за неявки и отражаться во внутреннем summary заявки. — Статус: `Не подтверждено пользователем`
- Перед реализацией нужно проверить production-данные по ФИО и оценить риск однофамильцев, опечаток и разных написаний одного участника. Источник истины - свежие production-данные, не локальные исторические выгрузки. — Статус: `Не подтверждено пользователем`

## Повторные заявки и участие в нескольких датах

- Один человек подает одну активную заявку на серию показов одного спецмероприятия. — Статус: `Зафиксировано`
- Если заявка уже допущена и участвует в розыгрыше, повторная подача с тем же ФИО/контактами должна быть отклонена сообщением, что заявка уже участвует в розыгрыше. — Статус: `Зафиксировано`
- Повторная подача должна проверяться до дорогостоящей OCR/LLM-обработки фото, если ФИО, email или телефон уже есть в заявках этого спецмероприятия. — Статус: `Не подтверждено пользователем`
- После успешной отправки форма должна блокировать повторный submit в текущей вкладке и показывать код уже принятой заявки. — Статус: `Не подтверждено пользователем`
- Участник может выбрать несколько дат в одной заявке. — Статус: `Зафиксировано`
- Участник может победить только один раз в рамках серии показов одного спецмероприятия. — Статус: `Зафиксировано`
- Если участник выиграл один показ, он исключается из розыгрышей остальных выбранных дат. — Статус: `Зафиксировано`
- Если дата показа уже прошла, список победителей считается утвержденным; эти победители не могут участвовать в розыгрышах на другие даты этого спецмероприятия. — Статус: `Зафиксировано`
- Участник, который стал победителем опубликованного розыгрыша любого спецмероприятия, больше не участвует в розыгрышах других спецмероприятий, включая будущую экскурсию в зоопарк. — Статус: `Не подтверждено пользователем`
- Возможность пользовательского обновления уже поданной заявки до дедлайна пока не включается; если понадобится, это отдельное требование. — Статус: `В доработке`

## Переиспользование паспорта для будущих спецмероприятий

- Аналогичная механика заявки на розыгрыш планируется для экскурсии `Премьера новой тематической экскурсии по Калининградскому зоопарку`. — Статус: `Зафиксировано`
- Система должна хранить проверенный профиль участника фестиваля отдельно от конкретной заявки: нормализованное ФИО, контакты, история загруженных фото, результат OCR, зачтенные штампы и timestamp последней проверки. — Статус: `Не подтверждено пользователем`
- Для нового спецмероприятия участнику не нужно заново прикладывать старые фото, если уже сохраненный профиль содержит достаточное количество зачтенных штампов для допуска. — Статус: `Зафиксировано`
- Участник должен иметь возможность добавить новые фото к уже существующему профилю, потому что к моменту следующего спецмероприятия у него может быть больше штампов. — Статус: `Зафиксировано`
- Новый анализ должен пересчитывать суммарные уникальные штампы по старым и новым фото, не засчитывая дубли повторно. — Статус: `Зафиксировано`
- Баллы и штрафы пересчитываются на момент подачи заявки на конкретное спецмероприятие, а не навсегда фиксируются первым OCR. — Статус: `Зафиксировано`

## Розыгрыш

- Розыгрыш запускается за сутки до соответствующего показа. — Статус: `Зафиксировано`
- В розыгрыше конкретной даты участвуют только допущенные заявки, где участник выбрал эту дату и еще не выигрывал другой показ этой серии. — Статус: `Зафиксировано`
- В розыгрыше конкретной даты участвуют только допущенные заявки, где участник выбрал эту дату и еще не выигрывал опубликованный розыгрыш любого другого спецмероприятия. — Статус: `Не подтверждено пользователем`
- Каждый балл участника добавляет один шанс в пул случайного выбора. — Статус: `Зафиксировано`
- Админский результат розыгрыша должен явно показывать механику честности: `1 балл = 1 билет`, общее количество билетов в раунде, выпавший номер билета, диапазон билетов победителя и источник случайности. — Статус: `Не подтверждено пользователем`
- Сохраненный результат розыгрыша должен содержать audit trail выбора победителя без ручной интерпретации: диапазоны билетов участников на момент раунда, выбранный билет и победителя этого билета. — Статус: `Не подтверждено пользователем`
- Один участник не может занять больше одного места в одном розыгрыше. — Статус: `Зафиксировано`
- Розыгрыш должен сохранять snapshot участников, баллов и выбранных дат на момент запуска. — Статус: `Не подтверждено пользователем`
- Нужно разделить черновой пересчет и опубликованный результат. — Статус: `Зафиксировано`
- Черновой пересчет можно запускать повторно без уведомления победителей. — Статус: `Зафиксировано`
- Опубликованный результат считается активным списком победителей и используется для уведомлений. — Статус: `Зафиксировано`
- Повторный опубликованный розыгрыш до даты показа допускается только как осознанное админское действие и создает новый `draw_run`, не затирая историю предыдущего результата. — Статус: `Не подтверждено пользователем`
- После наступления даты показа опубликованный список победителей считается финальным. — Статус: `Зафиксировано`

## Закрытие доступа к заявке

- После опубликованного розыгрыша конкретной даты эта дата должна стать недоступной для новой заявки: чекбокс disabled, рядом показана причина закрытия. — Статус: `Не подтверждено пользователем`
- Если дата показа уже прошла, эта дата должна стать недоступной для новой заявки независимо от статуса розыгрыша. — Статус: `Не подтверждено пользователем`
- Если все даты спецмероприятия недоступны, кнопка отправки формы должна быть disabled и не должна давать технической возможности отправить заявку. — Статус: `Не подтверждено пользователем`
- API сохранения заявки должно повторно проверять доступность выбранных дат и отклонять попытку отправить закрытую дату, даже если пользователь вручную изменил HTML или использует старую вкладку. — Статус: `Не подтверждено пользователем`

## Уведомления и Telegram-бот

- При создании новой заявки на розыгрыш суперадмины должны получать Telegram-уведомление через общий `telegram_outbox`, аналогично обычной регистрации. — Статус: `Не подтверждено пользователем`
- Уведомление о новой заявке должно показывать ФИО, спецмероприятие, выбранные даты, статус допуска, количество распознанных штампов, баллы, количество найденных обычных регистраций и неявок. — Статус: `Не подтверждено пользователем`
- Победителю направляется письмо на email или звонок по телефону. — Статус: `Зафиксировано`
- Результат розыгрыша должен поступить админу в Telegram: краткий список победителей и XLSX-таблица. — Статус: `Не подтверждено пользователем`
- В боте нужна команда `/spec`, показывающая все заведенные спецмероприятия, даты показов, квоты, статус заявок и статус розыгрыша. — Статус: `Не подтверждено пользователем`
- В админском Telegram-интерфейсе до проведения розыгрыша должна быть кнопка или раздел со списком ФИО допущенных заявителей по конкретному показу, с баллами, штампами, кодом заявки и количеством выбранных дат. — Статус: `Не подтверждено пользователем`
- В админском Telegram-интерфейсе должна быть команда или кнопка проверки живости процессов спецмероприятий: количество элементов в очередях OCR/LLM и Telegram/outbox по статусам, возраст самого старого ожидающего элемента, время последнего успешного и последнего ошибочного события по очередям, а также понятный итог `в порядке` или предупреждение, если есть зависшие/старые элементы. — Статус: `Не подтверждено пользователем`
- Даже если розыгрыш уже был, админ может запустить повторный черновой пересчет или повторный опубликованный розыгрыш до даты показа. — Статус: `Зафиксировано`
- Админ может посмотреть список победителей и по каждому победителю запросить список фото паспортов участника фестиваля. — Статус: `Не подтверждено пользователем`
- Ссылки на фото выдаются только админу для сверки и не являются публичными пользовательскими ссылками. — Статус: `Зафиксировано`
- В MVP Telegram-бот может отправлять админу фото паспортов файлами из private storage без генерации публичных ссылок. — Статус: `Не подтверждено пользователем`

## Хранение фото и персональных данных

- Фото паспортов участника фестиваля хранятся в Яндекс Object Storage. — Статус: `Зафиксировано`
- Публичные ссылки на фото пользователю или внешним посетителям не выдаются. — Статус: `Зафиксировано`
- Админские ссылки на фото должны быть доступны только в закрытом админском Telegram-сценарии. — Статус: `Зафиксировано`
- Нужно определить, будут ли админские ссылки presigned-ссылками с коротким сроком жизни или проксированными backend-ссылками с проверкой прав. — Статус: `В доработке`
- Consent-текст заявки должен явно покрывать загрузку фотографий паспорта участника фестиваля, распознавание текста и автоматический AI-анализ изображений для проверки права участия в розыгрыше, без технических аббревиатур в пользовательском тексте. — Статус: `Не подтверждено пользователем`
- Нужно определить срок хранения фото после окончания всех связанных спецмероприятий. — Статус: `В доработке`

## Отладка и выкладка

- Пока идет отладка, форма подачи заявки доступна по секретной ссылке и состоянию availability; после подтверждения готовности функционал переносится на публичный доменный URL, а возможность отправки заявки регулируется датами, розыгрышами и API-проверками. — Статус: `Зафиксировано`
- На главной странице в hero-ротации должен появиться первый блок о том, что открыта заявка на розыгрыш билетов на премьеру и показы спектакля `Этюды той весны`, с CTA на секретную preview-ссылку. — Статус: `Не подтверждено пользователем`
- Hero-блок со спецмероприятием должен участвовать в той же таймерной ротации, что и текущий hero, а не ломать существующее переключение. — Статус: `Не подтверждено пользователем`
- Hero-блок со спецмероприятием на главной странице должен использовать подготовленное изображение `etudy-toy-vesny-immersive-hero` как фоновую подложку, а CTA должен честно отражать live-доступность заявки: при доступных датах вести к форме заявки, при закрытии всех дат быть визуально disabled и не обещать подачу заявки. — Статус: `Не подтверждено пользователем`
- Текст и CTA в hero-блоке со спецмероприятием не должны перекрывать лица персонажей на изображении; desktop и mobile композиции нужно проверять отдельно. — Статус: `Не подтверждено пользователем`
- В мобильной версии hero-блока со спецмероприятием кнопки можно выравнивать вправо и частично накладывать на верхнюю дымовую часть изображения, чтобы сократить высоту блока и поднять картинку; при этом кнопки не должны перекрывать лица персонажей, сам паровоз и его прожектор, а между текстом и головами персонажей должен оставаться безопасный, но не чрезмерный отступ. — Статус: `Не подтверждено пользователем`
- Hero-блок со спецмероприятием должен делать смысловой акцент на формулировке `Иммерсивный спектакль на Южном вокзале на основе реальных историй переселенцев`, а CTA должен отвечать на пользовательский вопрос `как попасть`, сохраняя честное состояние доступности заявки. — Статус: `Не подтверждено пользователем`
- Hero-блок со спецмероприятием не должен выносить условия участия фразой `Попасть можно...` в body-текст; условия участия раскрываются через CTA и внутренний блок заявки. — Статус: `Не подтверждено пользователем`
- Внутри пользовательского пути к заявке нужно явно объяснить: попасть на спектакль могут те, кто активно ходил на события фестиваля; если 5 посещений еще не набрано, еще не поздно выбрать события в программе и прийти; после 5 посещений нужно вернуться к заявке на розыгрыш; подать заявку можно до `24 июня 2026`. — Статус: `Не подтверждено пользователем`
- Preview-форма должна визуально соответствовать основному сайту фестиваля: использовать фирменные шрифты, теплую бумажную палитру, мягкие карточки, понятные выбранные состояния дат и удобную мобильную компоновку. — Статус: `Не подтверждено пользователем`
- Секретная preview-страница спектакля `Этюды той весны` должна показывать тематическое изображение спектакля как видимую фотографию в первом экране и как фоновую подложку hero-зоны; это же изображение должно быть основной фотографией события в общей ленте и на странице события. — Статус: `Не подтверждено пользователем`
- Секретная preview-страница заявки на спектакль должна начинаться с текста о самом спектакле, а не только об условиях участия: реальные истории первых переселенцев, Южный вокзал как место памяти о начале пути, первые годы на новой земле, чувства/вера людей и взаимодействие с настоящими музейными вещами должны быть сформулированы в SSR-тексте страницы. — Статус: `Не подтверждено пользователем`
- В карточке `Этюды той весны` в общей ленте вместо бейджа `Бесплатно` нужно показывать условие участия: `для тех кто посетил 5 и более событий фестиваля`; поверх фотографии в карточке спецмероприятия не нужно добавлять затемнение, потому что на изображении нет текста. — Статус: `Не подтверждено пользователем`
- На странице события `Этюды той весны` основной путь пользователя должен вести к одной форме заявки на розыгрыш, а не к обычной регистрации на простое событие; состояние кнопки должно обновляться по live API спецмероприятия. — Статус: `Не подтверждено пользователем`
- Описание события `Этюды той весны` должно быть вовлекающим и профессиональным: основываться на реальных историях первых переселенцев, роли Южного вокзала как места памяти о начале переселения, переживании первых лет на новой земле, чувствах/вере людей и взаимодействии зрителей с настоящими музейными вещами, а не реквизитом. — Статус: `Не подтверждено пользователем`
- Старые неактуальные preview-выкладки по уникальным ссылкам можно очистить, чтобы уменьшить количество лишних медиафайлов в bucket. — Статус: `Зафиксировано`
- Очистка preview-артефактов не должна затрагивать production tickets, exports, registration state и текущие опубликованные файлы сайта. — Статус: `Зафиксировано`
- Перед закрытием визуальных задач по форме нужна проверка desktop и mobile через Playwright. — Статус: `Не подтверждено пользователем`
- Перед открытием регистрации нужно выполнить E2E-прогоны формы с загрузкой фото паспорта участника фестиваля в нескольких комбинациях выбора дат, а также Telegram/admin-сценарий розыгрыша и симуляцию каскада розыгрышей по датам с общим пулом участников. — Статус: `Не подтверждено пользователем`

## Защита от перегрузки и злоупотреблений

- Пользовательский и серверный контуры заявки должны ограничивать количество фотографий паспорта участника фестиваля в одной проверке и одной заявке, чтобы нельзя было отправлять сотни файлов. — Статус: `Не подтверждено пользователем`
- Backend должен проверять не только размер каждого файла, но и суммарный размер фотографий в запросе, количество multipart-частей и количество фото/`photoData`-частей до запуска OCR/LLM; весовые лимиты должны пропускать нормальный сценарий с пятью телефонными фото и не быть искусственно маленькими. — Статус: `Не подтверждено пользователем`
- OCR/LLM-вызовы должны проходить через ограниченную очередь с предохранителем: при налёте или переполнении очереди пользователь получает спокойное сообщение о временной перегрузке, а новые expensive-запросы к нейросети не создаются до разгрузки. — Статус: `Не подтверждено пользователем`
- Для endpoint-ов проверки фото и отправки заявки нужны отдельные rate limit-ы поверх общего лимита приложения; ограничения должны защищать production, но не менять availability-state события без явной команды владельца. — Статус: `Не подтверждено пользователем`
